# AIエージェント開発における統治状態の連続性

**MANOSUBE Agent Civilization OSの設計と公開開発記録の分析**

愁猴（SHUKOU）｜設計・経験報告 公開議論用草稿 第2版｜2026年10月7日

## 要旨

AIエージェントの長期にわたる開発・運用では、会話や実行履歴が保存されても、目的、操作権限、完了判定の根拠が次の実行主体に正しく継承されるとは限らない。本稿は、この問題を「統治状態の連続性」として定義し、MANOSUBE Agent Civilization OSの設計、公開実装、既存比較資料、実装者選択の開発記録を分析する。同システムは八段階の循環を通じて、目的、許可された変更、検証対象に結び付いた証拠、未解決差分を共通の正規状態へ接続する。分析から、目的と対象の識別、権限の範囲との結び付け、証拠の対象と鮮度の保持、未解決事項の継承という四つの不変条件を整理した。既存の事前固定比較では、直接実行と正規循環の両条件が二つの単純課題に成功した。さらに、Copilotによる一行のテスト追加には、実装、レビュー、人間の受理、マージ、変更後状態の確認を結ぶ公開記録が存在する。これらは比較手順と限定された開発循環の実行可能性を支持する。信頼性や安全性の一般的な優位性を測定したものではない。本稿の貢献は、状態永続化や認可の既存技術を、開発上の意味と受理条件に結び付ける設計・実装事例、およびその便益を検証するための反証可能な評価課題の提示である。

キーワード：AIエージェント、ソフトウェア工学、統治状態、認可、証拠、長期実行、再現可能性

## 1. はじめに

AIエージェントは、コードの編集、外部ツールの操作、複数工程の計画を一つの実行過程にまとめる。しかし、実行が長期化するほど「何をするか」「何をしてよいか」「何をもって完了とするか」の関係が複雑になる。モデルの更新、会話の圧縮、実装者の交代、環境の変更が起きても、その関係が維持されなければ、同じプロジェクトに参加しているように見えるエージェントが異なる前提で行動する。

**中心命題は、実行の継続に加えて、変更を許可し完了を受理する根拠の継続を設計する必要がある、ということである。** 状態を外部に保存するだけでは、この関係が維持されるとは限らない。

実務報告では、長期作業における進捗状況の見失いや早すぎる完了宣言が論点となっている[［1］][1]。研究においても、多エージェントシステムの失敗にはタスク検証や主体間の不整合が含まれる[［7］][7]。ただし、これらの観察から直ちに「すべての失敗は状態管理で解決できる」とは言えない。モデル能力、環境の不確実性、問題設定自体の誤りも独立した原因となる。

本稿は、対象をAIエージェントによるソフトウェア開発の統治に限定する。中心となる問いは、実行主体が変わるときに、目的、操作範囲、未解決課題、採用済み判断、完了根拠をどのように同じ正規状態へ接続するかである。ここでいう統治は、法律上の制度や組織統治全般ではなく、プロジェクト内で変更を認め、証拠を受理し、未解決事項を残すための技術的・運用的規則を指す。

MANOSUBE Agent Civilization OS は、その規則をエージェントの会話履歴から分離し、状態と遷移の構造として保持する公開プロジェクトである[［16］][16]。名称に含まれる「OS」は、汎用カーネルやハードウェア管理の実装を意味せず、エージェント作業の統治基盤というプロジェクト上の呼称として用いられている。「Civilization」も本稿では社会制度の成立を実証する概念として扱わない。

本稿の貢献は三つある。第一に、統治状態の連続性を作業記憶や実行継続と区別し、主体交代に際して維持すべき四つの条件として整理する。第二に、目的・権限・証拠・未解決差分を共通の状態遷移へ接続する設計を、永続化、耐障害実行、認可、実行時制御の先行例との関係から位置付ける。第三に、事前固定比較と実装者選択の公開開発記録を分析し、記録の整合性、実行経路への接続、環境での強制を区別したうえで、次の比較評価を設計する。

## 2. 問題設定と分析方法

### 2.1 統治状態の連続性

作業記憶には、会話、途中の計画、ツール結果が含まれる。実行状態には、処理位置や再試行情報が含まれる。これに対して本稿の統治状態は、目的と評価条件、現時点の正規状態、観測の出所、未解決差分、許可と禁止、実行された変更、採用可能な証拠、次の作業への引き継ぎを含む。これらは重なり得るが、会話を復元しただけで権限の有効性や証拠の鮮度が保証されるわけではない。

例えば、実装者Aが「テストは通った」と記録し、実装者Bがその文章を読んで作業を終了する場合を考える。検証対象が別のコミットに変わっていれば、文章の保存は完了根拠の継承にならない。同様に、ある操作が許されていたという過去の会話は、新しい作業単位、別のファイル範囲、別の実装者に対する許可とは限らない。このような取り違えを、主張の意味と対象を結び付ける記録によって扱うことが本稿の問題設定である。

研究質問は次の三点とする。

- RQ1：統治状態を実行主体から分離するために必要な構造は何か。
- RQ2：その構造は既存のエージェント基盤や制御技術とどこで重なるか。
- RQ3：公開実装と既存記録は、どの範囲まで設計を支持するか。

### 2.2 資料と証拠の扱い

コードと既存比較資料の分析対象は、mainブランチのコミット `c8f7cecd13e32133e183df8b2131859c524207b1` に固定する[［16］][16]、[［17］][17]、[［18］][18]、[［19］][19]。実装者選択の事例については、PR #104、PR #107、およびIssue #106の開発記録を別に扱う[［20］][20]、[［21］][21]。PR #107の受理・マージ・変更後状態の確認は固定コミットの後に行われており、同じ版のコードに含まれる事実として混同しない。Web資料と開発記録の確認日は2026年10月7日とする。

証拠は、設計記述、コードの静的確認、作者によるテスト・実行報告、保存された実行資料、独立した外部再検証に分類する。この区分は証拠の強さを単純に順位付けするものではなく、どの推論が可能かを明確にするためのものである。静的確認は規則の存在を示せるが、実際の全経路で強制されることまでは示せない。実行報告は当該環境の結果を示すが、異なる環境に結果を一般化するためには追加証拠が必要である。

新たなエージェント実験や全テストの再実行は行っていない。関連研究は、長期実行、状態永続化、認可、検証、プロンプトインジェクション、評価の信頼性との関連に基づいて選定した。検索対象と採否基準を網羅的に固定した系統的レビューではない。コードの静的確認、保存資料の検算、作者側の実行報告、独立したモデル実行の追試は、それぞれ異なる証拠として扱う。

## 3. 関連研究と2026年の技術的背景

### 3.1 長期実行と永続的なエージェント基盤

Anthropic の長期エージェントに関する報告は、初期化、進捗記録、増分的作業、検証を含むハーネス設計を論じている[［1］][1]、[［2］][2]。これらは、モデル単体の能力と、モデルを作業に接続する仕組みを分ける点で本稿と重なる。MANOSUBEの分析上の焦点は、進捗記録を保存することに加えて、その記録を正規の目的、許可、差分、採用済み証拠へどのように結び付けるかにある。

LangGraphのPersistence機能は、チェックポイント、スレッド、状態の復元、人間の介入などを扱う[［3］][3]。Temporal は、障害後の再開や長時間の待機を含む耐障害実行を提供する[［4］][4]。したがって、外部状態の保存、再開、実行主体の継続性は、本システムだけの新規技術ではない。これらの基盤上でも本稿の統治規則は実装できる可能性があり、競合製品というより、抽象度の異なる設計として比較する必要がある。

さらに、Anthropic のManaged Agentsは、永続的なセッション履歴と、置き換え可能なハーネスの分離を記述している[［15］][15]。これは「状態を主体の外に置く」という主張に直接重なる。本稿はこの先行例を踏まえ、状態の保存場所を実行主体の外に置くことを新規性として主張しない。検討対象は、プロジェクト上の意味を持つ目的・権限・証拠を、共通の遷移規則に接続する統合設計である。

### 3.2 認可と環境による強制

Cedar は構造化された認可ポリシーの評価を扱う[［5］][5]。MANOSUBEのAuthorityも、自然言語による自己申告をそのまま許可に変換するのではなく、記録を規則に照らして評価する点で重なる。ただし、認可判断を返すことと、実際のプロセスが禁止操作を実行できないことは異なる。

Anthropic の封じ込め設計は、プロンプトによる指示に加えて、環境側の境界を設ける必要性を示している[［14］][14]。この視点は本システムの限界にも直結する。Authorityが拒否を返しても、エージェントが別経路でシェルやネットワークを自由に使えるなら、Kernelの外では操作の制約が強制されない。認可評価、操作の仲介、資格情報の隔離、ファイルシステムの制約は別々に検証すべき構成要素である。

OWASPのAgent Control Standard（ACS）は、フレームワークをまたぐミドルウェアフックと、実行時に強制される宣言的な制御を扱う[［22］][22]。認可や監査をエージェントの外側で制御する方向は、MANOSUBEだけの問題設定ではない。本稿の焦点は、その制御を目的、検証対象、閉鎖判断、未解決差分の継承へ結び付ける契約にある。ACSとの直接の統合や比較実験は本稿の対象外である。

### 3.3 失敗分類、攻撃、実務課題評価

Cemriらは多エージェント実行の失敗を分析し、システム設計、主体間の不整合、タスク検証に関する分類を提示する[［7］][7]。Wangらの2026年プレプリントは、長期課題における破綻箇所を複数の領域で分析する[［11］][11]。これらは、会話の一貫性と課題完了を別々に評価する必要性を支持するが、MANOSUBEの有効性を検証した研究ではない。

AgentDojoは、ツールから得られる外部データを通じたプロンプトインジェクションと、防御による有用性への影響を評価する[［8］][8]。本システムに対する含意は、観測内容をAuthorityの根拠として無条件に受理しないことである。ただし、構造化しただけで攻撃が消えるわけではない。エージェントが悪意あるデータを正当な目的や承認として登録できるなら、入力側の境界が破られる。

TheAgentCompanyは、企業内の作業を模した環境でエージェントを評価する[［9］][9]。この方向は、本システムの将来の評価を、簡単な出力生成から、複数操作・承認・成果物を伴う課題へ拡張する際に参考になる。OWASPのAgentic Applications向け資料は実務上の脅威整理を提供する[［13］][13]が、特定実装の効果を立証する実験資料とは区別する。

### 3.4 成功率を超える評価と制御ループ

METRの研究ノートは、time horizonがAIの連続稼働時間ではなく、人間が課題を遂行する際の所要時間を基準とした指標であることや、推定の不確実性を説明している[［10］][10]。Khanalらの2026年プレプリントは、単発の成功と反復実行時の信頼性を区別する評価を提案する[［12］][12]。同論文は、評価した条件では記憶用の補助構造が長期課題の性能を損ねたとも報告している。状態の追加が常に有益であるとは仮定できない。MANOSUBEの評価でも、単発の成功数に加え、誤った完了受理、交代後の継承、繰り返し実行時のばらつき、記録・検証の費用を測定する必要がある。

監視、分析、計画、実行と知識を結ぶ自律管理の考え方にも先行例がある[［6］][6]。MANOSUBEの循環はこの系譜に位置付けられるが、段階名の違いだけでは新規性にならない。本稿で検討するのは、認可と証拠の受理、未解決差分の継承、主体交代を一つのプロジェクト状態に結び付ける具体的な契約である。

## 4. 状態中心統治の設計

### 4.1 正規状態と三つの境界

本システムの設計では、Kernel、正規状態バックエンド、Adapterの三つの領域を区別する[［16］][16]。Kernelは規則と評価の意味を保持する。正規状態バックエンドは追記型のイベントと、そこから得られる現在状態を保持する。Adapterはエージェント、GitHub、実行環境などとの接続を担当する。会話やGitHubの表示は、正規状態を参照する表示面または入力経路として位置付けられる。

「一つの状態所有者」はどの状態を正規とみなすかという論理的な位置付けを指す。単一の物理サーバーを必須とする主張ではない。一方、複数の保存先がそれぞれ独立に正規とみなされれば、採用判断が分岐する。どの記録が正規状態を更新し、どの記録が単なる報告なのかを決めることが、状態所有の役割である。

人間によるProject Bindingは、目的、境界、権限を設定する出発点となる。エージェントは、その枠内で観測、提案、変更、証拠の生成を行う。本稿では、プロジェクトの設定記録を指す場合はProject Binding、記録どうしの対象・識別子・範囲の対応を指す場合は「結び付け」と記す。実装者の能力の高さは許可の根拠にならず、交換可能な実装者を選ぶには、役割の適格性に加えて対象と範囲を特定した選択記録が必要となる。

### 4.2 八段階の循環

Objectiveは目的と受理条件を明示し、Stateは採用済み判断と現在状態を保持する。Observationが対象を観測し、Differenceが目的との差を特定する。Authorityはその差を扱う操作の可否を評価し、Changeは認められた変更を記録する。Evidenceは変更結果を検証可能な資料に結び付け、Reflowは証拠と未解決差分を正規状態へ戻す。本稿でいう「残差」は、この循環の後に残る未解決差分を指す。

図1 八段階の循環。Lineageは遷移を横断して記録する。

Lineageは九番目の工程ではなく、これらの遷移を横断して記録する系譜である。どの目的、状態、観測、許可、変更、証拠に基づいて次の状態が成立したかを追跡する。履歴を保存すること自体ではなく、対象と判断を結び付けることが目的となる。

この循環を開発作業に当てはめると、テスト修正の要求はObjective、失敗ログはObservation、期待との差はDifference、変更可能なファイルと操作はAuthority、修正コミットはChange、固定された対象の実行ログはEvidence、差分の閉鎖、または未解決差分としての維持はReflowに対応する。テストが通ったという文章だけでは、この接続のすべてを代替できない。

### 4.3 本稿が抽出する不変条件

設計から、主体交代に際して維持すべき四つの不変条件を抽出する。

- I1 目的と対象の識別：変更の根拠となる目的と、変更・検証の対象を特定できる。
- I2 権限の範囲：許可が実装者、作業単位、操作、範囲に結び付き、候補としての適格性と当該作業での選択を区別できる。
- I3 証拠の対象と鮮度：証拠が検証対象に結び付き、古い成功を新しい対象へ無条件に転用しない。
- I4 未解決事項の継承：完了した差分と未解決差分を区別し、交代後にも未解決事項が失われない。

統治状態の連続性は、会話の文章が同じであることではなく、交代後にもI1〜I4の関係を再構成し、次の変更と完了判定に利用できることとして捉える。これらは分析上の要求であり、全実装経路について形式的に証明された定理ではない。対応する記録・評価経路が存在することと、それらが常に正しく機能することは区別する。

## 5. 公開実装と強制境界

### 5.1 Authority評価

固定版のAuthority engineは、入力が明示的に与えられる評価器として実装されている[［17］][17]。評価時刻も入力であり、評価器自体がファイルシステム、ネットワーク、現在時刻から暗黙に情報を取得する構造ではない。評価経路は、要求とDifferenceの受理、Authority記録の受理と識別、対象との結び付けの照合、禁止規則、認可規則と最低限の条件、承認記録の照合と除外条件、出所の確認、決定という順序を持つ。禁止規則を認可規則より先に評価することで、認可規則に合致したことだけを理由に拒否条件を飛ばす経路を避ける。

この構造は、同じ入力に対する判断を検査しやすくする。しかし、入力が真実であることを保証しない。評価器の役割は許可判断であり、その場で変更を実行したり、状態を閉じたりすることではない。操作の仲介が評価結果に従うことは、評価器とは別の責務である。

### 5.2 実装者の選択

Executor selectionは、ELIGIBLE（候補としての適格性）とSELECTED（当該作業単位での選択）を区別する[［17］][17]。ただし、固定版の開発用BindingではClaude Codeが既定であり、非既定のCopilotに選択記録を要求する。したがって、任意の実装者が完全に対称に扱われる実装としては記述できない。Kernelの提供者中立性と、このリポジトリを開発する際の実装者選択は別の層である。

選択の検査は、リポジトリ、ブランチ、base/head、Difference、採用判断、操作、ファイル範囲を結び付ける。APIから読み戻した情報の受領記録（API read-back receipt）との内部整合性も検査するが、オフライン評価器がGitHub上の承認の実在や許可内容を自ら認証するわけではない。URLの形式、受領記録の整合性、外部サービス上の権限の真正性を、それぞれ別に確認する必要がある。

### 5.3 EvidenceとClosure

Reflowの閉鎖判定（closure）の実装にはG1からG22までの検査がある[［17］][17]。対象に結び付いた新しい観測からDifferenceを再導出し、十分な証拠に基づいて閉鎖可能かを評価する。実装境界も明示されており、例えば`required_observation_scope`が非nullの条件はG9でBLOCKEDとなる。G19の評価器は固定された不変条件レジストリとの一致を検査するが、任意のGitコミット・ツリーに対する出所の解決をその場で行うものではない。評価時点の鮮度検査と、Reflowのコミット直前の鮮度再検査も別の責務である。

閉鎖検査は、完了宣言だけで差分を消すことを避けるための仕組みである。検査数は正しさの証明にはならない。観測範囲が狭ければ未観測の失敗は残り、ハッシュが一致しても内容の真実、発行者の真正性、継続的な鮮度までは保証されない。

### 5.4 完成度を段階別に捉える

プロジェクトは、設計済み、実装済み、静的な確認またはテストによる確認、統合済み、通常の利用経路で到達可能、実行時の実証、人間による受理を区別している[［16］][16]、[［18］][18]。v1.0.0の受理と公開は、指定された製品境界での到達点であり、普遍的な自律性や実運用の安全性、比較上の優越性を意味しない。未解決差分FD-0005などが非阻害事項として残ることとも両立する。

### 6.2 測定範囲と未解決差分

FD-0005に記録されている測定の不足は、八段階の循環ではなく、八つの比較評価軸に関するものである[［18］][18]。評価軸は、誤完了の減少、長期状態保持、実行環境への到達、人間による再説明、手戻り、安全な実装者交代、権限逸脱、証拠の完全性である。完全測定は0軸、部分測定は「権限逸脱の減少」と「証拠の完全性」の2軸、未測定は6軸と記録されている。部分測定はハーネスの振る舞いに関する証拠であり、十分な課題分布を用いた効果の推定ではない。Codex単独および既存フレームワークの比較条件は、実呼び出し能力や資格情報の制約により成立していない。

Phase21のプロジェクト内受理は所定の開発ゲートへの到達であり、研究上の外的妥当性は異なる課題・主体・環境にも結果を一般化できるかという問いである。FD-0005は、両者を混同せず、未成立の比較や未測定の評価軸を未解決のまま維持する記録である。

## 7. 考察

### 7.1 AI業界の問題との重なり

関連資料は、エージェントの能力に加えて、永続的な実行基盤、環境での制約、検証可能な成果、反復実行時の信頼性を扱っている[［10］][10]、[［11］][11]、[［12］][12]、[［13］][13]、[［14］][14]、[［15］][15]、[［22］][22]。MANOSUBEの問題設定は、これらのうち、作業の意味と受理条件をプロジェクト状態へ結び付ける部分に位置付けられる。例えば、実装者が交代しても、旧コミットの成功が新コミットの完了根拠に変わらず、旧作業への許可が別範囲の操作へ拡張されないことが求められる。

この要求は、長期実行における未解決事項の継承、複数主体における助言・実装・承認の区別、外部入力と権限の分離、対象に結び付いた完了判定にまたがる。本システムはこれらを共通の循環に組み込む。その有用性は、既存の永続化・認可・実行時制御を備えた比較対象に対して、同じ課題と費用条件で検証する必要がある。

### 7.2 現段階での研究貢献

現段階の貢献は、統治上の意味を構造化し、実装経路と証拠の対応を追跡できる設計・経験報告である。既存技術でも同様の構成を実装できる可能性があり、外部状態、認可、制御ループの存在そのものを新規性とはしない。検討対象は、目的と対象、操作の許可、証拠の鮮度、閉鎖判断、未解決差分の継承を一つの遷移契約に接続する具体的な構成である。

公開コードと開発記録は、この構成を批判・検証するための材料となる。特に、実装の欠陥がどの境界で生じ、何を変更すると検査経路に接続されるかを追跡できることは、再利用可能な設計知識につながる。一方、同じプロジェクト内の改善履歴だけでは、統治設計が欠陥を減らしたという因果効果は推定できない。比較対象と反証条件を明示した評価が、設計事例から効果の実証へ進むために必要である。

### 7.3 次に検証すべき仮説

将来の検証仮説を次の四つに分ける。

- H1 完了判定：正規循環は、正しい完了を受理する能力を維持しながら、誤った完了受理を減らす。
- H2 状態継承：主体交代後にも、目的、許可、未解決差分を維持できる。
- H3 権限境界：実装者選択と操作範囲の結び付けは、許可範囲外の操作の受理を減らす。
- H4 運用費用：これらの効果は、遅延、費用、人間の確認負担を含めても有用である。

これらは本稿の実験結果ではなく、反証可能な評価課題である。

評価では、同一課題群を直接実行、永続化のみ、認可のみ、完全な正規循環の条件で比較し、状態保存と追加の統治規則の効果を分ける。完全条件から閉鎖判定、選択記録との結び付け、Reflowを一つずつ外す比較も行う。モデルの版、ツール、資格情報、許可範囲、費用上限、乱数シードまたは反復識別子、停止条件を事前に固定する。比較対象には環境での強制条件も明記し、Kernel評価器への要求の拒否と、実環境における無許可操作の防止を別に測定する。

課題には、古いテスト結果、誤ったhead、権限範囲外のパス、攻撃的なツール出力、変更途中での主体交代、観測不能な外部条件を含める。真の完了条件を独立に定義し、システムの受理結果と比較する。正しい受理、誤受理、誤拒否、未完了、権限逸脱、継承の欠落、所要時間、費用、人間の介入を報告する。反復間および課題間の依存関係を考慮し、不確実性を示す。必要標本数は予備評価と効果量の見積りから決め、現在の二課題を大規模実証として扱わない。

表3 将来評価における仮説と判定方法

| 仮説 | 主な測定 | 反証または不利益の判定 |
| --- | --- | --- |
| H1 完了判定 | 独立判定で未完了の試行のうち受理した割合と、完了試行の正しい受理率 | 誤受理が減らない、または正しい受理率が許容幅を超えて低下する |
| H2 状態継承 | 交代前に固定した目的・許可・未解決項目の欠落や誤った変更 | 比較条件に対して継承の誤りが減らない |
| H3 権限境界 | 許可範囲外の要求の受理率と、実環境での無許可操作の発生率 | 評価器で拒否されても別経路で操作が成立する |
| H4 運用費用 | 遅延、API・計算費用、人間の介入時間と件数 | 便益に対して事前に定めた許容費用を超える |

完了の独立判定は、システムの受理結果を参照せずに行う。成功条件、非劣性の許容幅、費用上限、誤拒否の許容範囲は結果を見る前に定める。

## 8. 限界と妥当性への脅威

構成概念の妥当性には、設計上の「十分な証拠」と現実の課題成功のずれがある。Objectiveが誤っている場合、正規状態に一貫して接続された失敗も起こり得る。観測が不完全なら、閉鎖検査を通っても現実の残差が存在し得る。統治状態の整合性と、目的の適切さや成果の社会的価値は別の問いである。

内部妥当性への脅威には、条件間で手順や人間の支援が異なり得ること、作者が課題と実装の両方を設計していること、レビュー記録に学習効果が含まれることが含まれる。既存比較は因果効果を分離する計画になっていない。大量のテスト成功数を累積しても、対象が重複したり、同じ前提を共有したりすれば、独立した実証件数にはならない。

外的妥当性は、同一の実行主体と申告された二つの短い課題、および一つの限定されたCopilot作業単位に制約される。後者には人間による操作と受理が含まれる。長期運用、複数組織、敵対的入力、他モデルへの交代は十分に測定されていない。製品版の公開や個別作業の受理を、これらの未検証事項を補う証拠とは扱わない。

強制境界の限界も大きい。Kernel外の操作を自由に行える実行環境では、ポリシー評価だけで逸脱を防げない。字句上は安全と判定されたパスも、シンボリックリンク（symlink）や実ファイルシステムの解決結果まで保証しない。記録の追記型構造や内容ハッシュも、管理者による改変、発行者の偽装、誤った観測をすべて防ぐものではない。

運用上は、記録・検証の費用、承認待ち、状態の肥大化、正規状態更新の競合、障害時の可用性が課題となる。厳しい受理条件が正しい変更を拒否する場合や、確認負担が増えて人間の判断が形骸化する場合も評価対象である。目的変更、例外承認、緊急作業についても、状態を壊さずに扱えるかは別途検証が必要となる。

関連研究は目的的に選定しており、一部は査読前プレプリント、企業の技術報告、研究ノートである。GitHubのmainやPRコメントは更新され得るため、コードは固定コミット、個別の開発事例は対象head・マージコミット・記録URLに結び付けて読む。後の変更は、新しい版として報告する。

## 9. 結論

AIエージェント開発における統治状態の連続性とは、実行主体が変わっても、目的と対象、権限の範囲、証拠の対象と鮮度、未解決事項を次の判断に接続できることである。本稿は、この問題を四つの不変条件として整理し、MANOSUBE Agent Civilization OSの設計・実装・公開開発記録との対応を示した。

既存資料は、構造化した認可評価、閉鎖検査、実装者選択、比較手順、および限定されたCopilot開発循環の実行可能性を支持する。二つの比較課題の成功結果は両条件で等しく、八つの比較評価軸の測定も未完了である。次に検証すべきことは、主体交代や誤った完了受理を含む反復比較において、統治状態を共通の遷移規則へ接続することが、既存技術に対してどの便益と費用を持つかである。
